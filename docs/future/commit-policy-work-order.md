# commit policy — work order

*Implements `docs/future/commit-policy.md`. Four stages, each gated by terminus and `make test` before Michael reviews it.*

## grounding notes

Facts established against the code that shape the plan below; where one bends a spec sentence, it is flagged in the stage that owns it.

- **`git.Pull` already preflights dirt itself** (`git.go:74`) and returns `ErrDirtyWorkingTree` — but its check is `IsDirty`, which counts untracked files, stricter than the spec's rule (untracked-only dirt does not pause the pull). The check moves to tracked-only dirt in stage 2. The relaxation is invisible under policy `all`: untracked files are staged and committed before the pull ever runs.
- **`sync()`'s `ErrDirtyWorkingTree` branch says "shouldn't happen since we committed above"** and quietly resets to `Watching`. Under `regions`/`none` the assumption is false by design; the agent-level pull decision (stage 3) is what keeps the branch unreached, and the branch itself is rewritten as the mid-cycle-race handler rather than a dead apology.
- **Git only detects a rename once it is staged.** The partition reads status *before* staging, so a move appears as a deletion plus an untracked file, classified independently. A move out of a region commits the deletion and squawks the new path; nothing is lost — the old content is in history, the new content is on disk. The spec's rename sentence describes an index-side view the partition never has; flagged for a one-line spec correction.
- **A bare `git commit` commits the whole index**, so operator-staged out-of-region files — mid-triage, preparing their own commit — would be swept into sexton's commit, and an index check before the commit is only a race against further staging (the operator's, or a `pre_commit` hook's). The boundary therefore lives on the commit itself: under `regions`, sexton makes a *partial commit* (`git commit -- <pathspec>`, git's default `--only` mode), which builds the commit from the named paths alone regardless of index state and leaves every other staged entry untouched. Operator-staged out-of-region work is just tracked out-of-region dirt: it raises attention and waits, unswept. [round 1, CP-R1-001]
- **`git.Commit` gates on `IsDirty` (tree), not on staged content.** Safe here because the commit block only runs when the in-region partition is non-empty and staging just succeeded; no change to `Commit`.
- **`parseStatus` reads line-oriented porcelain, which is ambiguous for hostile filenames** — C-quoted paths would defeat prefix matching, and a literal ` -> ` inside a name is indistinguishable from the rename arrow no matter how carefully lines are unquoted. Stage 2 switches the read to NUL-delimited porcelain (`-z`), which has no quoting at all; the fix also cleans quoted names out of today's alert file lists.
- **The `recovered from error` announcement is suppressed in shipped code.** `sync()` tests `state == Error` at cycle end, but its own top already set `Syncing`, so the check never passes on the normal recovery path; the existing test pins the suppression, and `docs/current/sync-loop.md` documents the announcement as working. An existing defect surfaced by round 1 review, fixed in stage 3 where the resting-state logic is rebuilt anyway.
- **The proto already carries state as a string** (`api/v1/sexton.proto:27`), so `attention` flows to both status surfaces without a wire change; a new `attention_detail` field is the only proto edit.
- **`NewContainer` wires `LogAlerter`; the Mattermost alerter is attached in `cmd/sexton/agent.go` (`buildAlerter`)** before `da.Run` starts the agents, but Mattermost `Start` ordering relative to the first sync is not guaranteed. Alert delivery is best-effort by posture and does not retry — and today a delivery failure is *invisible*: `Agent.alert` discards the alerter's returned error, contrary to the docs' claim that a failed post is logged. Stage 4 adds central failure logging so best-effort delivery leaves evidence when it misses. [round 1, CP-R1-006]

## stage 1 — config model and resolution

`internal/config/model.go`:

- `CommitPolicy string` and `CommitRegions []string` on `RepoDefaults`, `RepoEntry`, and `RepoLocalConfig`. No tags needed — `df/dd` binds `commit_policy`/`commit_regions` by name; never `yaml:` tags.
- `ResolvedRepo` gains `CommitPolicy string`, `CommitRegions []string`, and `PolicyDefaulted bool`.
- Policy constants: `PolicyAll = "all"`, `PolicyRegions = "regions"`, `PolicyNone = "none"`.

`internal/config/load.go`, in `Resolve`:

- Policy: `coalesce(local, entry, defaults)`; empty resolves to `PolicyNone` with `PolicyDefaulted = true`. An unrecognized value is an error naming the three valid ones.
- Regions: list-replace across the same three layers, the `resolveHooks` pattern. Normalization per region: reject empty, absolute, `.`, and any path that escapes the repo after `filepath.Clean` (a `..` prefix); strip a leading `./`; ensure a trailing `/` so prefix matching cannot let `journal-drafts/x` match region `journal/`. A region of the whole repo is rejected with a pointer to `commit_policy: all`.
- Validation: `PolicyRegions` with no resolved regions is an error (the silently-commits-nothing case, `validateLLM` precedent). A regions list under `all`/`none` is inert, per the spec.

`internal/agent/container.go`:

- Today a non-missing `.sexton.yaml` load error is warned and replaced with an empty local config, so the repo resolves from lower layers — under a global `all`, a corrupted override would auto-commit the whole tree. `NewContainer` now threads the load failure into resolution: the repo resolves with `CommitPolicy` forced to `PolicyNone` and `ResolvedRepo.LocalConfigError` carrying the parse error for the startup warning (stage 4). The repo stays visible, pulls, and commits nothing. [round 1, CP-R1-004]

Tests (`load_test.go` / new `resolve` cases): binding of both keys through real YAML (the dd-misspelling guard, per the `api_key` precedent); default-to-`none` with `PolicyDefaulted` set; explicit policy at each layer clearing the flag; region list-replace layering; each rejection; trailing-slash normalization pinned by a near-miss prefix case; a malformed repo-local file combined with a global `all` resolving to forced `none` with `LocalConfigError` set.

## stage 2 — git layer

`internal/git/git.go`:

- `IsDirtyTracked(ctx)` — `git status --porcelain -uno`, non-empty means tracked dirt (worktree or index).
- `Pull` preflight switches from `IsDirty` to `IsDirtyTracked`. Pin with a test that a pull proceeds over untracked-only dirt and still refuses over tracked dirt (both worktree-modified and index-staged).
- `StageRegions(ctx, regions []string)` — `git add -A -- <pathspec>...` with every region wrapped as `:(literal)<region>`, so a region name is never interpreted as a glob or pathspec magic. The caller passes only regions that contain dirty paths, so the pathspec-matches-nothing failure is unreachable; test staging of modifications, untracked files, and deletions inside a region while files outside stay untouched, plus a region name containing metacharacters.
- `CommitOnly(ctx, message string, regions []string)` — `git commit -m <message> -- <pathspec>...`, the same `:(literal)` wrapping: a partial commit of the region paths only, immune to whatever else the index carries. Policy `all` keeps the existing bare `Commit`. Accepted residual, by decision: native git hooks are out of scope — a repo-owned `pre-commit` hook that stages files during the partial commit could breach the boundary, but the fleet's repos carry no native hooks and no machinery is added for them (spec's deferred section carries the revisit conditions) [round 3, CP-R3-001, deferred]. Test that entries staged outside the regions survive the commit unswept and uncommitted, and — real git, not the mock — that a staged cross-boundary rename alongside an unrelated dirty path in the same region commits its in-region endpoint while the out-of-region endpoint survives staged. [CP-R2-003]
- Message input reads the commit *object*, not the index and not the mutable `HEAD`: `Show(sha)` (`git show --format= --diff-merges=first-parent --patch <sha>`), `ShowStat(sha)` (`git show --format= --diff-merges=first-parent --stat <sha>`, the oversize fallback), and `ShowNameStatus(sha)` (`git show --format= --diff-merges=first-parent --name-status -z <sha>`, NUL-parsed — the explicit `--format=` on all three keeps the placeholder commit's header out of the LLM input and the NUL parser [round 6, CP-R6-A01], and the explicit `--diff-merges=first-parent` keeps a multi-parent commit describable: git's default combined merge diff omits paths matching either parent, which would silently blank the message and file lists for an operator-started merge completed under `all` — first-parent reads as "what this merge brought onto the branch", pinned by a merge test whose changes match the second parent but not the first [round 7, CP-R7-001]. The NUL parser's tests also cover the variable-arity rename and copy records (`R100`/`C75` carry two path fields), pinning the score-bearing token, both paths, and destination-path categorization — a parser tested only on single-path records misaligns everything after the first rename [round 7, CP-R7-A01] — the same no-quoting discipline as the status read, with names escaped before they enter the alert file lists; one hostile committed-filename test) [round 5, CP-R5-A01]. The created commit's id is captured at creation — parsed from the commit invocation's own output and verified by reading the object's message back — so an operator commit landing afterward can never become the thing sexton describes. The pathspec-scoping of `DiffStaged`/`DiffStat` planned in round 2 is superseded: a read of the commit is inherently bounded, so staged out-of-region WIP cannot appear in any message path, and the one boundary is the commit itself. [CP-R1-003; CP-R2-001, superseded; round 3, CP-R3-003; round 4, CP-R4-001]
- `RewordCommit(ctx, branch, oldSHA, message string)` — builds the replacement object with `git commit-tree` (same tree, same parents, author preserved) and swaps it in with `git update-ref refs/heads/<branch> <new> <oldSHA>`: an atomic compare-and-swap that fails if the ref no longer points at sexton's commit. On failure nothing is touched and the mechanical message stands — sexton can never reword a commit it did not create. This replaces the `--amend --only` reword, whose target is whatever `HEAD` has become. Tests: an operator commit landing between description and reword (CAS refuses, operator commit untouched, sexton's commit keeps the placeholder), an outside entry staged between commit and reword leaving content unchanged, and an integration assertion that the replacement retains the original tree, every parent, and the author name, email, timestamp, and timezone — `commit-tree` inherits none of that automatically, and a regression would silently alter attribution and `last_change`. [CP-R4-001; round 5, CP-R5-A02]

`internal/git/status.go`:

- The status read switches to NUL-delimited porcelain (`git status --porcelain=v1 -z -b -uall`): fields are NUL-separated with no quoting, so every legal filename — spaces, quotes, backslashes, newlines, a literal ` -> ` — parses exactly, and the planned C-unquoting task disappears. In `-z` form a rename entry carries the new path with the old path in the following NUL field; `parseStatus` keeps per-entry detail — a new `Entries []StatusEntry{Path, OldPath string; X, Y byte}` alongside the existing category lists, which remain as-is for the alert and message paths. Tests pin each hostile filename above and both directions of staged cross-boundary renames. [round 1, CP-R1-002]
- An entry is *tracked dirt* when it is not purely untracked (`??`).
- The staged classifier counts every index-side code — `MADRCT`, type changes included — not just the obvious five.
- `Status` gains small helpers the partition will use: `TrackedPaths()`, and per-entry staged-ness — shapes settled in implementation, pinned by tests.

`internal/agent/agent.go` — the `gitClient` interface grows `IsDirtyTracked`, `StageRegions`, `CommitOnly`, `RewordCommit`, and the three by-SHA `Show*` reads; `DiffStaged`/`DiffStat` leave the message path; the agent test mock follows.

## stage 3 — the policy in the sync loop

`internal/agent/state.go`: `Attention` appended after `Holdout`; `String()` returns `attention`.

`internal/agent/agent.go`:

- Struct: `attentionDetail string`. Accessor `AttentionDetail()`.
- `setAttention(detail string)` — records the detail and alerts at severity `attention` when the detail differs from the last, and *never touches the displayed state*: mid-cycle the state stays `Syncing`, and `Attention` is applied only at return-to-rest by `restingStateLocked`. This is a deliberate divergence from `setError`, whose immediate state-set is correct because it always ends a cycle — `setAttention` never does, and a mid-cycle state flip would break snooze's am-I-interrupting-a-sync check (`state == Syncing`), letting a snooze that answers the attention ping display `snoozed` while the cycle pushes on. `clearAttentionLocked` companion; the announced recovery (an `info` alert, `local changes resolved` in spirit) fires from the cycle when a standing detail is found clear. [round 3, CP-R3-002]
- The attention detail string: sorted offending paths, capped at 10 with `+N more`, suffixed `(pulls paused)` when tracked out-of-region dirt stands, staged out-of-region entries counting as tracked dirt like any other. Deduplication rides the string, so a new path re-alerts; paths hidden behind the cap changing does not — accepted in the spec. Raw path bytes never leave the partition layer: the detail renders *every* name through `strconv.Quote`, unconditionally, so each path is one unambiguous quoted token — valid UTF-8, safe for the proto marshal and the rendered rows — and the framing metadata (`+N more`, `(pulls paused)`) sits strictly outside the quoted tokens. The whole detail string is thereby injective, which the deduplication key requires: with conditional quoting, a file named `a, b` renders like two files, and a file named `foo (pulls paused)` impersonates the pause suffix — collisions that would silently swallow a re-alert, including the one announcing that pulls just paused. Collision tests pin delimiter-like names and pause-suffix impersonation. [round 3, CP-R3-004; round 5, CP-R5-002]

`sync()` reworks around a partition evaluated on *every* cycle — a clean tree is simply an empty partition, not a branch that skips the evaluation — one code path for all three policies [CP-R2-002]:

1. Read a pre-staging `Status`; partition `Entries` against `CommitRegions` by prefix — under `all` everything is in-region, under `none` nothing is. Membership is per-endpoint: each endpoint of an entry classifies on its own side of the boundary, so a staged cross-boundary rename contributes its in-region endpoint to the commit set (and the message and file lists) and its out-of-region endpoint to attention and the tracked pull-pause. Git commits trees, not renames — a pathspec commit takes the in-region half of a staged rename no matter how the entry is labeled — so classification follows the tree, and committed content never depends on unrelated dirt. Staged and unstaged moves thereby behave identically. Old-path partitioning applies to `R` entries only: a copy entry (`C`, emitted under `status.renames=copies`) has an old path that is an unchanged source, not an endpoint of the change — pinned by one copy-status test. [CP-R1-002; round 2, CP-R2-003; round 3, CP-R3-A01]
2. Unmerged-path guard, unchanged, before any staging. `validateBranch` is already above; both conflict guards keep their jobs.
3. Commit block, only when the in-region partition is non-empty — **commit first, describe after** [round 3, CP-R3-003]: `pre_commit` hooks → `StageAll` under `all`, `StageRegions` (regions that own dirty paths) under `regions` → commit *immediately* with a count-free crash-safe placeholder message (`Commit` under `all`, `CommitOnly` with the literal region pathspecs under `regions` — the partial commit is the boundary: staging injected after the partition read cannot enter it [CP-R1-001]) → capture the created commit's SHA → build the final message *from that exact object* — the LLM summary (`Show(sha)`, `ShowStat(sha)` when oversize) or, with no LLM configured or a failed call, the mechanical message from `ShowNameStatus(sha)` — → `RewordCommit` compare-and-swap before anything pushes → `post_commit` hooks. The reword happens on every path, LLM or not: no published count or file name is ever derived from anything but the committed object, so a `pre_commit` hook adding in-region files or commit-time drift cannot skew the fallback message [round 4, CP-R4-002]. The `sync complete` file lists come from `ShowNameStatus(sha)`. A concurrent in-region edit during the LLM call lands in the *next* cycle's commit; a crash mid-flow or a refused swap leaves the placeholder — spartan, never wrong. The reword always precedes the pull, so a rebase never sees an about-to-be-reworded commit.
4. Attention evaluation, clean cycles included: out-of-region partition non-empty → `setAttention`; empty with a standing detail → clear and announce before the pull. The operator's resolution — committing the offending files — produces exactly the clean cycle this step must see, since `completeSync` deliberately retains standing attention. [CP-R2-002]
5. Pull decision: skip the pull when tracked out-of-region dirt stands (the partition knows tracked from untracked); otherwise pull as today. The `ErrDirtyWorkingTree` branch is rewritten as the mid-cycle-race handler: dirt appeared between the partition read and the pull — no error, state re-resolves, next poll re-evaluates.
6. Push, hooks, and completion. The push is always attempted when commits exist; a non-fast-forward rejection while pulls are paused lands in `setError` — the accepted compound in the spec's census. The completion alert changes one thing: the file-bearing `sync complete` alert **carries no SHA** — its message and file lists are labeled as sexton's created change, which is exactly what they describe, because by completion time a rebase may have rewritten sexton's commit and an operator commit may sit on top, so a terminal `ShortHEAD` could name a different commit than the metadata describes (and the captured SHA is equally invalid after a rebase). The status table's last-commit column keeps terminal `ShortHEAD` under its honest meaning: the repo's HEAD after the sync. Test: an operator commit landing after the reword but before completion. [round 8, CP-R8-001]

Precedence, mechanically: a single `restingStateLocked()` chooser embodies the *complete* precedence — active holdout, then pending or active snooze (applied only while the request-time `snoozeUntil` is still in the future — the timer started at the request and the expiry returned to the caller stays the truth; the chooser never starts or restarts a timer, and a blocked phase that outlasts the requested duration means the snooze has simply expired, so the chooser falls through [round 6, CP-R6-001]), then `errorDetail` → `Error`, then `attentionDetail` → `Attention`, else `Watching` — evaluated under the agent's lock. Every terminal path uses it and none carries private logic: `completeSync` (successful and no-remote completions included [round 5, CP-R5-001]), `setError` (which records the detail and then chooses like every other exit — a terminal error can never discard an operator's pause, and a snooze that arrived mid-phase rests the repo `snoozed` with the error detail retained beneath it [round 4, CP-R4-003]), the snooze-expiry branch inside `sync()`, `handleSnoozeExpiry`, holdout exit in `handleHoldoutTransition`, `clearCanceledSyncState`, and the expired-snooze and post-error-clear branches in `Resume` and `TriggerSync` [round 3, CP-R3-A02; round 4, CP-R4-A01]. The rule is absolute — no code assigns a rest state except through the chooser — and the chooser owning holdout and snooze itself is what ends the exit-by-exit patching: rounds 1 through 5 each found another terminal path with private logic. `setError` leaves `attentionDetail` intact. Holdout entry is untouched. [round 1, CP-R1-005]

Recovery detection is rebuilt while this logic is open, because it is broken today: `sync()` checks `state == Error` at the end of the cycle, but the top of `sync()` already set `Syncing`, so the documented `recovered from error` announcement never fires on the normal path — and the existing test pins the suppression. The fix captures whether an error detail stood at cycle entry, before the state is overwritten; a clean completion clears the error, retains any standing attention, and emits one recovery alert. The suppression-pinning test is corrected, and `docs/current/sync-loop.md`'s announced-recovery claim becomes true. [CP-R1-005]

Tests (mock git): `regions` happy path — in-region commit with scoped staging, out-of-region attention, pull skipped over tracked dirt; pull proceeding over untracked-only dirt; `none` never committing while pushing an operator-made commit; `all` producing today's call sequence; the partial commit excluding entries staged outside the regions after the partition read; a metacharacter region name staging and committing only its literal prefix; attention dedup, re-alert on a new path, announced recovery; error-outranks-attention and re-assertion after the error clears; snooze expiring onto a standing attention; holdout exiting onto a standing attention; recovery announced from the compound error-plus-attention case; the full attention arc — repo in attention, operator commits, the next clean cycle clears and announces; a staged cross-boundary rename splitting its endpoints between the commit set and attention; a snooze arriving after the attention evaluation but before the push — the cycle stops at the next boundary and nothing touches the remote once `snoozed` is displayed; an in-region tracked file modified between the commit and the message generation — message and file lists still describe the commit exactly (real git); `Resume` and `TriggerSync` over an expired snooze with standing attention resolving to `attention`, not `watching`; a `pre_commit` hook adding an in-region file with no LLM configured — the final mechanical message matches the commit exactly; a snooze arriving during a blocked push whose push then fails — the repo rests `snoozed`, error detail beneath, and no poll touches the remote until expiry; snooze and holdout transitions injected at the completion boundary of a *successful* cycle — the pause wins over `watching` and `attention`; a snooze whose duration elapses while the phase is still in flight — expired by cycle end, the chooser falls through and no timer is restarted.

## migration

Breaking on upgrade, by decision: unconfigured repos stop committing and warn at startup. The migration is in-repo only — every synced repo gains a `.sexton.yaml` stating its policy (`all` for the journal and dataset repos, `regions` for the grimoire, `none` for terminus-canon), and the repos propagate it across the fleet themselves; no host config changes. Ordering matters because config resolves at startup only: land the policy files first, then restart the daemons — a running daemon that pulls a new `.sexton.yaml` sits fail-safe at `none`, warning, until its restart [round 2, CP-R2-A01]. Live adoption of a changed repo-local config is carded on the roadmap (`adopt-repo-local-config-changes`). Nothing else changes shape; existing configs parse unchanged.

## verification

`make test` (tests plus `go vet`) green per stage; `terminus review --quality <ref>` per stage before Michael sees it, advisory pending sexton's canon onboarding. Stage 3 is the load-bearing review: the partition and the partial-commit boundary are where a mistake commits something it must not.

The stages are implementation checkpoints, not releases: stage 1 accepts configuration the loop does not yet honor, and stage 3 raises attention before stage 4 can display or deliver it, so no intermediate stage is deployed to the fleet — nothing ships until stage 4 completes. [round 4, CP-R4-A02]

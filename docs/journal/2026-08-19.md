# 2026-08-19

## api_key in the llm block

- The `llm` block now accepts `api_key`, so the LLM API key can live in the config file instead of only in the env var named by `api_key_env`. Resolution happens once in `llm.NewClient` at startup: a non-empty `api_key_env` value wins, otherwise the direct `api_key` is used. That is exactly the Mattermost `token`/`token_env` rule, so the two credential-bearing integrations share one documented precedence rather than inventing a second one.

- Deliberately no new validation: the one rejected combination remains `model` without `endpoint` (the v0.1.2 rule). An `api_key` with no endpoint is ignored, the same class as an `api_key_env` with no endpoint today — extending the load-time rejection to it would have converted tolerated fleet configs into startup failures, the exact failure mode v0.1.2's docs fix avoided.

- Pinned in tests: `client_test.go` covers direct key, env-wins, and empty-env fallback; `load_test.go` pins that `api_key` actually binds through `df/dd` (a misspelled or `yaml:`-tagged key would silently leave the client unauthenticated — the bearer header just stops being sent).

- Docs touched: README (example now shows `api_key`, table rows for both fields), `docs/current/configuration.md`, `docs/current/git-and-commit-messages.md`, changelog under Unreleased.
